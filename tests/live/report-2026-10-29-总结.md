## 2. 计量计费准确性结论

### 2.1 平台自身计算：准确

- 四条任务的 `quota = tokens × model_ratio × group_ratio` 复算偏差均为 **0.00%**。
- 单价执行精确：mini 11.5（=23 元/M）、fast 18.5（=37 元/M）均分毫不差。
- 差额结算方向正确：多退（C6 退款 1,981,350）、少补（C1 补扣 2,516,016）。
- 日志的 `quota` 字段是「本次变动额」而非「总额」，对账必须按 `task_id` 汇总并区分 type 2/6，否则会把退款当扣费（本轮脚本第一版即踩此坑）。

### 2.2 计量口径：2.0 异常，mini/fast 正常

- 同样 720p、5.088 秒、均带音轨：mini/fast 均 108,900 tokens（与公式差 -0.91%，属帧数取整），**2.0 为 217,392（+97.81%，约 2 倍）**。
- 排除项：时长（都 5.088s）、分辨率（都 720p，且**分辨率参数根本没传给上游**）、音轨（都有）、计费链路（同一套 adaptor）。
- 剩余解释：2.0 的 token 计量口径不同（疑似按 2× 帧率或双流计量），或渠道 1 的上游计费策略差异。**需向火山/渠道确认**。
- 业务影响：2.0 720p 5 秒实付 ¥10.00，按定价表推算应为 ¥4.97，**客户成本翻倍**。

### 2.3 预扣准确性：2.0 低估 50%

- C1 预扣按 108,000 tokens（¥4.968），终态补扣到 ¥10.0003。
- 预扣不足会让低余额用户透支；补扣失败即产生欠费（代码有 `unpaid_quota` 记录）。

### 2.4 折扣：未测

- 按用户要求暂缓。已观察到的旁证：2.0 被路由到渠道 16「字节跳动_7.7折_2.0专用」，说明 2.0 的折扣来自**渠道成本折扣**，与对外分组倍率是两套东西，后续需分别核对。

### 2.5 404 根因（补充，19:55）

| 探测 | 结果 | 结论 |
|---|---|---|
| 错误 key POST 上游 URL | **401 `Invalid API key in request`** | 路由存在，不是路径写错 |
| 带训练域名但去掉 `/volcengine` 前缀 | 404 `404 Route Not Found` | 路径前缀必须带 `/volcengine/api` |
| 平台实际请求体 | 仅 `model` + `content` | 与分辨率/时长参数无关 |
| C1 重跑（720p/5s，最小参数） | 仍 404（渠道 16） | 渠道 16 对当前 key 整体拒绝 |

结论：**渠道 16 的 404 是上游账号/模型权限问题**，不是 URL、也不是 1080p/10s 参数导致的。需要在提供方后台确认该 key 是否开通 `doubao-seedance-2-0-260128`，或先用文档里的 curl 拿同一把 key 直连复现。

## 5. 建议处理顺序

1. **修渠道 16**：核对 base_url、密钥、模型映射与上游是否支持 2.0；恢复前 2.0 的所有定价档位无法验证。
2. **确认 2.0 token 口径**：拿 217,392 这个数与火山/渠道对账，确认是 2× 帧率、双流还是渠道加价；若属正常口径，需同步修正定价表的「元/秒」折算与预扣估算。
3. **修 duration 透传**：`convertToRequestPayload` 增加 `req.Duration > 0` 分支；同时补 `metadata.duration` 兼容。
4. 恢复后补跑：C2（1080p）、含视频输入（验证 28/31/16 档位倍率是否生效）、折扣组对比。
