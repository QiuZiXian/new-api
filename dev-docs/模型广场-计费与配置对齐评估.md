## 0. 结论速览

| 目标详情页 | 需要的计费维度 | 现状可支撑度 | 判定 |
|---|---|---|---|
| 大语言模型（输入/输出/缓存 tokens） | token 多通道 | **可支撑** | ✅ 直接可用（含缓存/缓存写入/图像/音频通道） |
| 文生图 · 按输出张数 | 张数 | 半支撑（伪装成"按次"） | 🟡 数值能算，但单位/维度/审计都是错的 |
| 文生图/OCR · 按输出 token | token 多通道 | **可支撑** | ✅ 同上 |
| 视频 · 按输出秒数（多分辨率档） | 秒 + 分辨率档 + 多行 | **不可支撑** | 🔴 缺单位、缺多行、渠道内写死、无审计维度 |

一句话：**当前后端只有 3 种计费形态（per-token 倍率 / per-request 固定价 / tiered_expr 表达式），能完整表达的只有 1 种页面（大语言模型）。文生图靠"把张数塞进按次计费"勉强算数，视频按秒在数据模型层根本没有位置。**

已存在"计费配置 + 模型额外配置 = 展示"的雏形，但有三处结构性不齐：**双写来源、粒度错配、形态靠反推**。

## 1. 现状盘点：后端计量计费能力

### 1.1 三种计费形态与判定入口

唯一的判定点：`relay/helper/price.go:74`

```go
modelPrice, usePrice := ratio_setting.GetModelPrice(info.OriginModelName, false)
```

| 形态 | 判定条件 | 数据源 | 单位语义 | 适用链路 |
|---|---|---|---|---|
| **per-token（倍率）** | 不在 ModelPrice 表 → `usePrice=false` | `ModelRatio` + `CompletionRatio` + `CacheRatio` / `CreateCacheRatio` / `ImageRatio` / `AudioRatio` / `AudioCompletionRatio` | 隐含 `$/1M tokens`（底层约定 1 单位 = $0.002/1K，前端 ×2 换到 /1M） | 同步（文本 / 图像 / 音频 / embedding） |
| **per-request（固定价）** | 命中 ModelPrice 表 → `usePrice=true` | `ModelPrice` | 隐含"每次请求" | 同步 + 任务（视频） |
| **tiered_expr（表达式）** | `billing_setting.GetBillingMode(model)=="tiered_expr"` 且 expr 非空（**优先级最高**） | `billing_setting.billing_expr` | 表达式内每项是**真实 $/1M tokens** | **仅同步链路** |

优先级：`tiered_expr` > `ModelPrice` > `ModelRatio`。

> ⚠️ 注意 `ModelPriceHelper` 先判 `usePrice`，再判 tiered_expr（`price.go:74` vs `:79`）。两者同时配置时执行侧走表达式，但 `model/pricing.go:380-389` 反推出的 `Pricing.QuotaType` 仍是 `1` → **下发给前端的 quota_type 与真实计费形态不一致**（前端因 `isDynamicPricingModel` 优先判表达式而侥幸正确）。

### 1.2 三条执行链路

```
① 同步（文本/图像/音频/OCR）
   relay.ModelPriceHelper          → 预扣（估算 token 或 固定价×分组倍率）
   → service.PreConsumeBilling     → BillingSession 冻结
   → 上游返回 usage
   → service.PostTextConsumeQuota  → calculateTextQuotaSummary → SettleBilling（只结差额）

② 图像（n 张）
   controller/relay.go (dto.ImageRequest) → GetTokenCountMeta()
     relaykit/dto/openai_image.go:169  BillingRatios{"n": float64(imageN)}
   → 仅当 usePrice==true 时才注入（price.go:167）
   → 上游返回后 relay/channel/openai/relay_image.go:25-30 用真实张数覆盖 "n"

③ 任务（视频）
   relay/relay_task.go:182  helper.ModelPriceHelperPerCall  （固定价 或 倍率/2）
   → :191 adaptor.EstimateBilling → OtherRatios{"seconds","video_input","resolution","size"}
   → :198 ApplyOtherRatiosToFloat（TaskPricePatches 名单内跳过）
   → :206 预扣 + 提交即 SettleBilling
   → 轮询完成 service/task_polling.go:639-661
        AdjustBillingOnComplete 优先 → 否则按 TotalTokens 重算
```

**关键机制**：`types/price_data.go:74-86` — 所有 `OtherRatios` 是**匿名扁平乘数，连乘**：

```go
func (p *PriceData) OtherRatioMultiplier() float64 {
    multiplier := 1.0
    for _, ratio := range p.otherRatios { if isValid && ratio != 1.0 { multiplier *= ratio } }
    return multiplier
}
```

实测 key 全集：`n`、`seconds`、`size`、`resolution`、`video_input`。**没有 ID、没有单位、没有审计维度**，日志里只是平铺进 `other` JSON。

### 1.3 配置来源与热更新

```
硬编码默认值  setting/ratio_setting/model_ratio.go:26-304
              (defaultModelRatio / defaultModelPrice / defaultAudioRatio ...)
   ↓ InitRatioSettings()  main.go:299（AddAll，不是覆盖）
options 表 JSON  →  model/option.go:566-587  按 key 热更新

```

**上游价格同步**已存在：`controller/ratio_sync.go:142 FetchUpstreamRatios`，支持从上游 `/api/ratio_config` 拉 `model_ratio / model_price / billing_expr`，也支持 OpenRouter / models.dev 换算（`:724`、`:906`）。

## 2. 目标：4 种详情页究竟需要什么

把截图抽象成一张统一的"价格信息"表，每种页面的差异只在**四个字段**：

| 页面 | 功能列（分组） | 维度列（variant） | 单位 | 行数 |
|---|---|---|---|---|
| 大语言模型 | 缓存 tokens / 输入 tokens / 输出 tokens | 基础价格 | **/ M Tokens**（可切 K） | 3（缓存可选） |
| 文生图 | 输出 | 基础价格 | **/ 张** | 1 |
| OCR | 输出 | 基础价格 | **/ 张** 或 **/ M Tokens** | 1~N |
| 视频 | 输出（合并） | Fast快速·480p / Fast快速·720p / Pro高质·480p / Pro高质·720p / Pro高质·1080p | **/ 秒** | 1~N |

另外每行还带 4 个附属属性，截图里全都出现了：

1. **计费项 ID**（`glm-5.3-output-tokens` / `seedream-5.0-pro.image` / `seedance-2.0-video.fast.480p`）
2. **原价 + 现价**（¥2.00 划线 → ¥1.40）
3. **折扣标签**（7折 / 9.9折 / 7.0折）
4. **节省比例**（节省 30.0% / 1.2% / 0.7%）

> 也就是说：**排版布局本身不难，难的是"单位 + 多行 + 结构化折扣 + 稳定 ID"这四样后端一个都没有。**

## 4. 配置能力评估：两个配置面 & 三处不齐

### 4.1 现有两个配置面

| | **A. 模型广场配置** | **B. 计量计费配置** |
|---|---|---|
| 路由 | `/models/metadata` | `/system-settings/billing/model-pricing` |
| 页面 | `web/src/features/models/components/drawers/model-mutate-drawer.tsx` | `web/src/features/system-settings/models/model-pricing-sheet.tsx` |
| 落库 | `models` 表 | `options` 表 |
| 字段 | model_name / description / icon / tags / hot_label / discount_label / vendor_id / name_rule / endpoints / status + **内嵌 Pricing Configuration** | `ModelRatio` / `ModelPrice` / `CompletionRatio` / `CacheRatio` / `CreateCacheRatio` / `ImageRatio` / `AudioRatio` / `AudioCompletionRatio` / `billing_setting.billing_mode` / `billing_setting.billing_expr` |
| 编辑粒度 | **per-Model 记录**（靠 `name_rule` 可匹配一批真实模型名） | **per-真实模型名**（精确 key） |
| 形态切换 | 无 | 三 Tab：`Per-token` / `Per-request` / `tiered_expr` |

### 4.2 展示公式（现状）

`model/pricing.go:359-414` 的 `updatePricing()` 把三者拼在一起：

```
/api/pricing 输出
  = ability（渠道能力 → enable_groups / supported_endpoint_types）
  + models 表（description / icon / tags / hot_label / discount_label / vendor_id）
  + ratio_setting + billing_setting（quota_type / model_ratio / completion_ratio / 各 ratio / model_price / billing_expr）
```

**"计量计费 + 模型额外配置 = 展示"这个等式本身是对的**，问题在于实现细节。

### 4.3 三处结构性不齐 🔴

**① 双写来源：价格能在两个页面改**

`model-mutate-drawer.tsx:1035-1400` 内嵌了完整的 Pricing Configuration，而 `/system-settings/billing/model-pricing` 也能改同一批 `options` key。
→ 两个入口写同一份数据，**没有互斥、没有提示、没有审计**。管理员在 A 改完在 B 看不出来（或反之）。

**② 粒度错配：展示按规则匹配，计费按精确名匹配**

| 环节 | 匹配方式 |
|---|---|
| 展示（`pricing.go:196-239`） | `name_rule` = exact / prefix / suffix / contains → 一条 meta 覆盖一批真实模型名 |
| 计费（`price.go:74`） | `ratio_setting.GetModelPrice(info.OriginModelName)` — **精确 key**，只有 `gpt-4o-gizmo*` / `gemini-*-thinking-*` 有通配归并（`model_ratio.go:702-719`） |

→ **最危险的场景**：模型广场上看到"¥0.7/张"，实际请求 `doubao-seedream-5.0-pro-xxx` 时命中的是另一个 key 的价格；或者 meta 命中但计费表没配 → 直接返回 `model_price_not_configured`（`price.go:108`）。

**③ 形态靠反推，没有显式声明**

`QuotaType` 不是配置项，而是"是否在 ModelPrice 表里"的反推结果（`pricing.go:380-389`）。
→ 管理员在 UI 里点的是"Per-request Tab"，但落库只是往 `ModelPrice` map 里塞一个 key；
→ 想从"按次"改回"按 token"，必须**删 key**，UI 上没有直观表达；
→ 前端拿到 `quota_type` 后只能猜单位。

### 4.4 最接近"对齐"的现有答案：tiered_expr

表达式机制已经能做到"一种配置、两处消费"：

- **执行**：`ModelPriceHelper` → `modelPriceHelperTiered` → `p / c / cr / cc / img / ai / ao` 变量 + `tier("label", ...)` + `||| when(...) * 6` 请求规则
- **展示**：`billing_expr` 原样下发 → 前端 `billing-expr.ts` 解析出 `ParsedTier[]`（`tier` 的 label 就是"维度"列的文案）→ `dynamic-price.ts` 渲染主/次价格项
- **日志**：`InjectTieredBillingInfo()` 注入 `billing_mode / expr_b64 / matched_tier / request_rules`

**但它的表达能力被三件事卡住**：
1. 变量单位被锁死为 `$/1M tokens`（配额换算是 `rawCost / 1e6 * QuotaPerUnit * groupRatio`）→ 表达不了"张"和"秒"
2. 任务型（视频）链路根本不读 `billing_mode`
3. `/api/pricing` 只下发**单个** `billing_expr` 字符串，前端只有一个 Base Price 卡片能展示首档（`dynamic-price.ts:163` `tier = tiers[0]`）

## 5. 建议方案

### 5.1 收口到"计费项（BillingItem）"这个单一事实源

```
BillingItem {
  item_id        // 稳定 ID：glm-5.3.output-tokens / seedream-5.0-pro.image / seedance-2.0.video.fast.480p
  model_name     // 所属模型（支持 name_rule 展开）
  display_group  // 「功能」列：输出 / 输入 tokens / 缓存 tokens
  variant_label  // 「维度」列：基础价格 / Fast快速·480p
  unit           // token | image | second | request | char
  unit_scale     // 1_000_000 | 1_000 | 1     （token 专用，支撑 K/M 切换）
  price          // 现价（已折算到 unit × unit_scale）
  origin_price   // 原价，空则不渲染删除线
  enabled        // 是否展示
  billing_binding// 计量侧取值方式：{"var":"c"} | {"per":"n"} | {"multiplier_by":"resolution","table_ref":...}
}
```

- **计量侧**：`BillingItem` 是唯一录入点，保存时**反向编译**出 `ModelPrice` / `ModelRatio` / `billing_expr`，并做一致性校验（`setting/billing_setting/tiered_billing.go:73 SmokeTestExpr` 已有雏形）
- **展示侧**：`/api/pricing` 直接下发 `price_items[]`，前端**零计算、零猜测**
- 折扣标签/节省比例由 `origin_price / price` 自动算，不再手填

> 一个 BillingItem 集合 → 两个视图（计费执行 + 展示）。这才是真正的"对齐"，而不是靠两边手填一致。

### 5.2 分期落地（风险从低到高）

**Phase 0 — 打通展示（不动计量，1~2 天）**

后端：`model/pricing.go` 的 `Pricing` 加派生字段 `PriceItems []PriceItem`，在 `updatePricing()` 里**由现有 quota_type / ratio / price 合成**：

| 现有配置 | 合成出的 items |
|---|---|
| quota_type=0 | `输出 tokens`×1M、`输入 tokens`×1M、`缓存 tokens`×1M（有 cache_ratio 才出） |
| quota_type=1 且 endpoints 含 image 类 | `输出`×张 → 单位 `image` |
| quota_type=1 且 endpoints 含 video 类 | `输出`×秒 → 单位 `second` |
| billing_mode=tiered_expr | 每个 tier 一行，单位取 expression version 的默认（token） |

前端：`model-details.tsx:PriceSection`（`:569-781`）改为 **"有 price_items 就直渲染，否则回落旧分支"**，一行不动旧逻辑。

→ **效果**：4 种页面排版立刻全都能渲染，文本 / 文生图（按张）/ 视频（单档）立即正确。视频多档仍只有一行，按张的 `n` 语义问题仍未解决。

**Phase 1 — 打通视频按秒 & 多档（核心改造）**

1. **任务型接入表达式**：`ModelPriceHelperPerCall`（`:187-253`）增加 `billing_mode=="tiered_expr"` 分支，或新增 `billing_mode="task_variant"` 走 variant 表
2. **doubao 渠道常量上移**：把 `relay/channel/task/doubao/constants.go:32-77` 的 `videoPriceTable`（元/百万 token 的相对倍率）搬到配置层，成为该模型的 `PriceItems`，**管理员可改、可下发**
3. **OtherRatios 命名化**：`seconds` / `resolution` / `video_input` 从匿名乘数升级为带 ID 的维度，日志与展示同源
4. **`/api/pricing` 下发全部 tier**，前端详情页把多行表格（截图的视频样式）渲染出来

**Phase 2 — 收口配置面 & 补展示字段**

1. 移除 `model-mutate-drawer.tsx` 内嵌的 Pricing Configuration（或改为只读 + 跳转），定价只在 `/system-settings/billing` 编辑
2. `models` 表补 `context_length` / `category` / `capabilities`（前端 `types.ts:67-74` 的占位字段已就绪，**只差后端下发**）
3. 原价/现价/折扣结构化落库
4. `quota_type` 改为显式配置字段，不再反推

### 5.3 "后端先支持一种"选哪个

按你的要求"后端先基于已有能力支持一种即可" → **建议先做实【按输出 token 计费】**，理由：

1. **覆盖 4 类中的 3 类**（文本 ✅ / 文生图 ✅ / OCR ✅ / 视频部分 ✅），一次改动铺满大部分页面
2. **这是唯一有完整"预扣 → 真实用量回写 → 差量结算"闭环的形态**（`usage.completion_tokens` 可靠）
3. **按张、按秒都缺可靠的实际数量回写**：
   - 按张：`relay_image.go:25-30` 只在 `UsePrice` 时覆盖 `n`，且 `quota_type=0` 的图像模型**根本不乘 n**
   - 按秒：`doubao` 未实现 `AdjustBillingOnComplete`（`adaptor.go:110` 内嵌 `BaseBilling` 返回 0）→ **预扣即终价**
4. `tiered_expr` 的变量体系（`p/c/len/cr/cc/img/ai/ao`）和前端解析器（`billing-expr.ts` / `tier-expr.ts`）都已就绪，改造成本最低

**按张**作为第二步：用 `quota_type=1` + **显式的 `n` 维度**（需先修 `price.go:167` 让 `quota_type=0` 也尊重 `n`，或强制图像模型走固定价），并给 `n` 一个可展示的 ID。
**按秒**必须等 Phase 1。

## 7. 需要产品侧确认的 3 个决策

1. **视频的"多档"是一个模型多行，还是多个模型别名？**
   决定 `BillingItem.variant` 是"模型内子项"还是"模型级"。
   （现网方案是"相对倍率表写在渠道里"，但管理员改不了 → 从维护性看建议做成模型内子项。）

2. **折扣是手填还是自动算？**
   截图里同时出现"7折"和"节省 30.0%"，且 `¥2.00 → ¥1.40` 正好 7 折 → 大概率是自动算。
   自动算 = 只需录入 `origin_price` + `price`；手填 = 保留 `discount_label` 但要保证两处一致。

3. **"计费项 ID"是纯展示文案，还是要作为日志/账单维度键？**
   如果是后者，需要进 `consume_log.other` 并被 usage-log UI 引用（工作量 +1 档）。
